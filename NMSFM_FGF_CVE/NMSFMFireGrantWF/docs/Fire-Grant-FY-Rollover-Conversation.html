1. Creating FY2026 from FY2025 using the repo

Team question

In the database there is no data for FY2026. We know why this is true and the reason has no bearing on the resolution. Is it possible to create a new Fiscal Year for 2026 from the data that is available for FY2025 — and to do this using the repo we have?

Assistant response

Short answer: You can stand up some FY2026 data using this repo, but there is no single “clone FY2025 → FY2026” workflow. What gets created, and whether it comes from FY2025, depends on which tables you mean.

What this repo actually supports

The codebase treats “fiscal year” in two separate areas:

AreaMain tablesHow a new year gets created
Fire Grant (this web app)FGApplicationSettings, FGApplications, FG_App_*Lazy create for settings only; applications are new per department
Fire Protection Fund / FY distributionFYAllowableDist, FYStatuteDist, FYTotalDist, FYTotalDistCalc, FYApplication, etc.Lazy create when FPFService / FYDistService methods run for that year

There are no SQL rollover scripts and no admin “Copy fiscal year” button in the repo.

1. Fire Grant program settings (FGApplicationSettings) — partial

When anything calls GetFireGrantAppSettings(2026) and no row exists, the app creates FY2026 with hardcoded defaults, not from FY2025. Defaults include StartDate 7/1/year, EndDate 9/30/year, MaxGrantAmount 400000, and template legal/instruction text (see FGService.CreateNewFireGrantSettings).

Using the repo (no code changes):

  1. Log in as a web admin.
  2. Open Admin → Manage Settings.
  3. Pick 2026 in the fiscal year dropdown (list goes through DateTime.Now.Year + 1).

That triggers LoadSettings → GetFireGrantAppSettings(2026) → auto-insert if missing.

Limitation: Instructions, dates, max grant, eligibility PDF, and customized page content from FY2025 are not copied. Re-enter in Manage Settings or copy at the database level.

2. Fire Grant applications (FGApplications + FG_App_*) — not bulk-cloned

New applications are created empty via CreateNewApplication (one per department/FY). There is no service that duplicates FY2025 applications into FY2026.

The app does read prior-year data at runtime when a user fills out the current year (e.g. General Information pulls last year’s app for prefill). FY2025 rows help user prefill but do not populate FY2026 until each department starts a FY2026 application.

3. FPF / distribution FY tables — copies some fields from prior year

FPFService / FYDistService implement year rollover only when getters run for the target year (e.g. GetAllowableDistAsync(2026), GetStatuteDistsAsync(2026)):

  • FYStatuteDist: copies ISOClass, MSBaseAmount, SSBaseAmount from year 2025.
  • FYAllowableDist: new row for 2026; uses prior year’s FYStatuteDistribution (requires FY2025 row).
  • FYTotalDistCalc: copies structure from 2025 but recalculates station counts; amounts may reset.
  • FYTotalDist: creates one row per active department—not a full copy of FY2025 amounts.

The Fire Grant web project uses FPFService mainly for department/address lists, not for running FY seeding in normal admin flows.

Practical answer

GoalPossible with this repo alone?
FY2026 exists in dropdownsYes
FY2026 program settings rowYes (defaults, not FY2025 copy)
FY2026 settings matching FY2025No built-in; manual admin or DB copy
FY2026 department applications pre-created from FY2025No
FY2026 FPF/distribution from FY2025Partially via service layer if APIs invoked

Recommended path

  1. Confirm FY2025 is complete for whatever you need as source.
  2. Fire Grant: Admin → Manage Settings → 2026 → adjust content.
  3. Applications: Departments create FY2026 apps through normal flow unless you use custom DB/script.
  4. Distribution (if needed): Invoke FPFService getters for 2026 or DBA process.

2. Department apparatus & personnel before applications (FY2027)

Team question

We want everything that is associated to any department before the application is created. For instance all of the apparatus associated to a department from FY2025 to be available in FY2026. We don't care if there are any applications in FY2026. We only care if the apparatus and personnel associated to a department are available when creating FY2027. Does that make sense? And, are personnel and apparatus all that is needed to start FY2027?

Assistant response

Yes, your goal makes sense. You want department-associated operational data (especially apparatus) to carry forward without maintaining a full FY2026 grant year. The app is built around per-year applications, but several screens read from prior applications at runtime instead of a department master inventory.

How apparatus and “personnel” are stored

Neither is a department + fiscal year master list. Both live on a Fire Grant application (FGApplications), keyed by ApplicationId:

What you meanWhere it lives
ApparatusFG_App_Apparatus + FG_App_ApparatusEquipment → ApplicationId
Personnel (in this app)No separate roster table. Counts and chief/contact on FG_App_GeneralInfo (NumberOfFirefighters, FFI_Firefighters, FFII_Firefighters, etc.) — per ApplicationId
Department identityCodepal Addresses, FG_FDIDs, parties — not fiscal-year-specific

You do not need FY2026 rows to “hold” apparatus or personnel for FY2027. You need FY2025 (or earlier) applications with that data saved, plus a FY2027 application shell when a department starts the new cycle.

Apparatus — mostly matches what you want

When someone opens Apparatus for a new FY2027 application with no FY2027 apparatus saved yet, the UI calls GetPriorFGApplicationApparatusAsync, which loads from the most recent other application for that department (highest FiscalYear first).

If there is no FY2026 application, FY2025 is used and the grid shows “Information Loaded from Previous Application.”

Caveats:

  • A FY2027 FGApplications row must exist (Instructions → Accept).
  • Data is UI prefill until the user saves Apparatus.
  • If a FY2026 application exists but has no apparatus data, the code still picks that app first and does not walk back to FY2025.

Personnel (firefighter counts) — different rule; FY2026 gap hurts

On General Information, prefill uses exactly prior fiscal year (Session FiscalYear − 1), not “most recent application.”

For FY2027, that is FiscalYear == 2026 only. If there is no FY2026 application, firefighter counts are not prefilled from FY2025.

Apparatus and personnel do not behave the same in this codebase.

Is apparatus + personnel all you need to start FY2027?

No — for the grant cycle to work end-to-end. Minimum for department + apparatus + headcount-style personnel:

RequiredNotes
FGApplicationSettings for FY2027Auto-created with defaults when first accessed
Per department: FGApplications for FY2027Created when department accepts instructions
FY2025 application with saved apparatusFG_App_ApparatusEquipment on that ApplicationId
FY2025 application with saved general infoOnly helps FY2027 personnel prefill if logic is fixed or stub FY2026 exists — skipping FY2026 blocks prefill as written
Department master dataAddress, FDID, web users — not FY-specific
Global reference dataFG_Categories, FG_Priorities — not per FY

Other sections (Training, Budget, PPE, documents, etc.) do not use the same “load from prior year” pattern. FYAppStation (FPF module) is year-keyed separately—not Fire Grant apparatus.

Direct answers

  • Does your goal make sense? Yes.
  • FY2025 apparatus for FY2027 with no FY2026 apps? Yes for apparatus, if FY2025 data is saved and no empty FY2026 app blocks rollover.
  • FY2025 personnel for FY2027 with no FY2026 apps? Not with current General Information logic.
  • Are apparatus and personnel all that is needed? No. You need FY2027 settings, FY2027 application per department, and FY2025 saved data as source; personnel across a skipped year needs a code or data fix.

3. Simplest workable / programmable solution

Team question

I need a workable, programmable or scripted or other, solution to this issue. The simplest possible, if there is such a thing.

Assistant response

Here is the simplest workable path, ordered from least moving parts to most complete.

Recommended: one hook when the FY2027 application is created

Idea: When a department accepts instructions and CreateNewApplication runs, immediately copy apparatus + general info (personnel counts) from the latest prior application that has data (e.g. FY2025), not from “FY − 1” only.

Why simplest overall:

  • One place in code (FGApplicationService.CreateNewApplication, after SaveChangesAsync).
  • Same rule apparatus already uses (OrderByDescending FiscalYear).
  • Data is in the database before anyone opens a page.
  • Skipping FY2026 is fine; FY2025 remains the source.

What to copy (minimum)

Source (e.g. FY2025)Target (new FY2027 app)
FG_App_GeneralInfoNew Id, new ApplicationId
FG_App_ApparatusNew Id, new ApplicationId
FG_App_ApparatusEquipmentNew ApparatusId per row, new ApplicationId

Rules: Only copy if target has no row yet; walk prior years newest-first until data found; do not copy signatures, scores, review, submitted status, or granted amounts.

Also once per environment: Ensure FGApplicationSettings exists for FY2027 (Admin → Manage Settings or GetFireGrantAppSettings(2027)).

Effort: ~one service method + call from CreateNewApplication.

Alternative: one-time SQL script (no app deploy)

INSERT…SELECT with NEWID() per department from FY2025 → FY2027. Pros: no C# release. Cons: exact table names, backup required, re-run care, future creates won’t auto-copy.

What not to rely on

ApproachWhy insufficient
UI-only prefillGeneral Info only FY−1; apparatus doesn’t persist until Save
Only fix General Information displayDisplay only; no DB copy until Save
Bulk empty FY2026 applicationsBlocks apparatus (newest empty app picked first)
Copy entire FY2025 applicationsWrong status/signatures for new cycle

FY2027 checklist (minimal)

  1. FGApplicationSettings for 2027 exists.
  2. Each department gets FY2027 FGApplications (Instructions or script).
  3. Baseline copy runs (hook or SQL) → general info + apparatus on that ApplicationId.
  4. Departments verify and update for the new year.

Bottom line: Simplest durable fix = post-create copy in CreateNewApplication. Simplest no-deploy fix = one-time SQL for those three tables.
